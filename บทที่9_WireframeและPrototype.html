1. บทนำ

“ต้นแบบที่ดีคือคำถามที่จับต้องได้ ไม่ใช่คำตอบสุดท้าย” — เราสร้างต้นแบบเพื่อ ‘ทดสอบไอเดีย’ ด้วยต้นทุนต่ำ ก่อนจะลงทุนเขียนโค้ดจริง แล้วต้นแบบควรละเอียดแค่ไหนจึงจะพอดี?

ตลอด 8 บทที่ผ่านมา เราเข้าใจผู้ใช้ ออกแบบโครงสร้าง วางเลย์เอาต์ และกำหนดสี/ตัวอักษรครบแล้ว บทนี้คือจุดที่ทุกอย่างมารวมกันเป็น ต้นแบบ (Prototype) ที่กดเล่นได้จริง และเป็นบทที่เชื่อมโลกของ “การออกแบบ” เข้ากับโลกของ “การพัฒนาเว็บ” โดยตรง

เนื้อหาแบ่งเป็น 2 ส่วน: ส่วนแรกว่าด้วยการสร้าง wireframe และ prototype ตั้งแต่ความละเอียดต่ำถึงสูง ส่วนที่สองเป็นสิ่งที่หลายคนข้าม — การนำต้นแบบไปสร้างเป็นหน้าเว็บจริง ด้วย HTML/CSS

💭 ชวนคิดก่อนเริ่ม
ถ้าต้นแบบหน้า “แจ้งสัตว์หาย” กดแล้วไม่มีอะไรเกิดขึ้นเลย ผู้ทดสอบจะบอกอะไรเราได้บ้าง? และถ้ามันโต้ตอบได้เหมือนจริง เราจะได้ feedback ต่างออกไปอย่างไร?

2. Wireframe และ Prototype

2.1 ระดับความละเอียดของต้นแบบ (Fidelity)

ต้นแบบมีหลายระดับความละเอียด เลือกใช้ตามวัตถุประสงค์และช่วงเวลาของงาน ยิ่งช่วงต้นยิ่งควรหยาบและเร็ว (แก้ง่าย ทดสอบไอเดียโครงสร้าง) ยิ่งช่วงท้ายยิ่งละเอียด (ทดสอบรูปลักษณ์และการโต้ตอบจริง)

ระดับลักษณะใช้ทดสอบเครื่องมือ
Lo-fi
Wireframe		ขาวดำ กล่อง/เส้น ไม่มีสีจริงโครงสร้าง การจัดวาง การไหลกระดาษ, Figma, Balsamiq
Mid-fi
Mockup		มีสเกล/สัดส่วนจริง เริ่มมีสีบางส่วนลำดับชั้น ความหนาแน่นของข้อมูลFigma
Hi-fi
Prototype		สี ตัวอักษร รูปจริง โต้ตอบได้รูปลักษณ์ การโต้ตอบ usabilityFigma (prototype mode)

2.2 Wireframe — โครงร่างความละเอียดต่ำ

Wireframe คือโครงร่างหน้าจอแบบเรียบง่าย เน้น “อะไรอยู่ตรงไหนและสำคัญแค่ไหน” โดยตั้งใจตัดสีและรายละเอียดทิ้ง เพื่อให้ทีมโฟกัสที่โครงสร้างและการจัดวาง ไม่ใช่ความสวยงาม ทำให้แก้ไขได้เร็วและถูก

กรณีศึกษา

Wireframe ของแอปค้นหาสัตว์เลี้ยงหายเริ่มจากหน้าที่สำคัญที่สุดก่อน (หน้าแรก, แจ้งสัตว์หาย, รายละเอียดประกาศ) โดยอ้างอิงจากการจัดวางในบทที่ 7 ทุกองค์ประกอบยังเป็นกล่องขาวดำ

2.3 Interactive Prototype — เชื่อมจอให้กดได้

Prototype ที่โต้ตอบได้ เกิดจากการนำหน้าจอหลายหน้ามา “เชื่อม” กันด้วยจุดเชื่อม (hotspot) เพื่อจำลองการกดและการเปลี่ยนหน้าจริง ทำให้ทดสอบ user flow กับผู้ใช้ได้โดยยังไม่ต้องเขียนโค้ด แนวคิดหลักได้แก่ hotspot (พื้นที่ที่กดได้), การเปลี่ยนหน้า (transition) และ สถานะ (state)

2.4 สถานะของหน้าจอ (Screen States)

หน้าจอจริงไม่ได้มีแค่สถานะ “ปกติ” ต้นแบบที่ดีต้องออกแบบสถานะอื่นด้วย เพื่อให้ครอบคลุมสถานการณ์จริง สถานะที่พบบ่อยได้แก่ Empty (ยังไม่มีข้อมูล), Loading (กำลังโหลด), Error (เกิดข้อผิดพลาด) และ Success (สำเร็จ)

⚠️ ข้อผิดพลาดที่พบบ่อย
  • ออกแบบเฉพาะสถานะปกติ ลืม empty/loading/error ทำให้ผู้ใช้สับสนเมื่อเจอสถานการณ์จริง
  • ทำ hi-fi ละเอียดเกินไปตั้งแต่ต้น ก่อนทดสอบโครงสร้าง — เสียเวลาแก้
  • prototype สวยจน “ขายฝัน” ผู้ทดสอบเข้าใจผิดว่าเป็นของจริงที่ทำงานทุกปุ่ม
💻

3. จาก Prototype สู่หน้าเว็บจริง

ส่วนนี้คือสะพานสำคัญระหว่างการออกแบบกับการพัฒนาเว็บ ต้นแบบใน Figma ยังไม่ใช่เว็บจริง — มันเป็น “ภาพที่กดได้” แต่ไม่มีโค้ดที่ทำงานเบื้องหลัง การเปลี่ยนต้นแบบให้เป็นเว็บจริงต้องผ่านกระบวนการ ส่งต่องานออกแบบ (Design Handoff) และการเขียนโค้ด

3.1 Design Handoff — ส่งต่ออะไรให้นักพัฒนาบ้าง

เพื่อให้นักพัฒนาสร้างหน้าเว็บได้ตรงกับที่ออกแบบ นักออกแบบต้องส่งมอบข้อมูลที่ชัดเจน ได้แก่

สิ่งที่ส่งมอบรายละเอียด
ค่าระยะและขนาด (Specs/Redlines)ระยะห่าง (spacing) ขนาดองค์ประกอบ ความกว้างคอลัมน์ — อ้างอิงกริดจากบทที่ 7
Design Tokensชุดสีและ type scale ในรูปตัวแปร (จากบทที่ 8) เพื่อให้โค้ดใช้ค่าเดียวกัน
Assetsไอคอน รูปภาพ โลโก้ ส่งออกเป็นไฟล์ (SVG/PNG) พร้อมใช้
States & Interactionsพฤติกรรมของปุ่ม (hover, กด), สถานะ empty/loading/error, การเปลี่ยนหน้า
Flowลำดับการเชื่อมหน้าจอ (จาก User Flow บทที่ 6)

3.2 จับคู่องค์ประกอบออกแบบกับเทคโนโลยีเว็บ

แต่ละสิ่งที่ออกแบบไว้มี “คู่” ในโลกของโค้ด การเข้าใจการจับคู่นี้ทำให้ส่งต่องานได้ราบรื่นและช่วยให้นักออกแบบสื่อสารกับนักพัฒนาได้

ในต้นแบบ (ออกแบบ)ในเว็บจริง (โค้ด)
โครงสร้าง/องค์ประกอบหน้าจอHTML ที่สื่อความหมาย (semantic) เช่น <button>, <form>
การจัดวาง/กริด (บทที่ 7)CSS Layout — Flexbox / Grid
สีและตัวอักษร (บทที่ 8)CSS + ตัวแปร (design tokens)
การเชื่อมหน้า/hotspotลิงก์/เส้นทาง (routing) หรือ <a href>
การโต้ตอบ/สถานะJavaScript (เปลี่ยนสถานะ, ตรวจฟอร์ม)

3.3 ตัวอย่าง: แปลง “การ์ดประกาศสัตว์หาย” เป็นโค้ดจริง

เราจะนำการ์ดประกาศที่ออกแบบไว้ มาเขียนเป็น HTML/CSS จริง โดยใช้ design tokens จากบทที่ 8 เริ่มจาก โครงสร้าง HTML ที่สื่อความหมาย

<!-- โครงสร้าง (HTML) — สื่อความหมายและเข้าถึงได้ -->
<article class="post-card">
  <img class="post-card__img" src="dog.jpg" alt="สุนัขสีดำ ชื่อน้องดำ">
  <div class="post-card__body">
    <div class="post-card__row">
      <h3>น้องดำ</h3>
      <span class="badge badge--lost">หาย</span>
    </div>
    <p class="post-card__meta">หายที่ ซอย 5 · เมื่อวานนี้</p>
    <button class="btn btn--primary">ส่งเบาะแส</button>
  </div>
</article>

จากนั้นใส่ สไตล์ (CSS) โดยอ้างอิง design tokens (สี/ตัวอักษร) จากบทที่ 8 และเทคนิคจัดวางจากบทที่ 7

/* ใช้ตัวแปรจาก Style Guide บทที่ 8 */
.post-card { border-radius: 14px; overflow: hidden;
  box-shadow: 0 4px 14px rgba(31,55,89,.12); background:#fff; }
.post-card__img { width:100%; height:140px; object-fit:cover; }
.post-card__body { padding:14px 16px; }
.post-card__row { display:flex; justify-content:space-between; align-items:center; }
.badge--lost { background: var(--color-error); color:#fff;
  padding:3px 10px; border-radius:20px; font-size:.75rem; }
.btn--primary { width:100%; background: var(--color-accent);
  color:#fff; border:none; padding:11px; border-radius:10px;
  font-family: var(--font-base); font-weight:600; cursor:pointer; }

ผลลัพธ์ที่เรนเดอร์จริงด้วย HTML/CSS ข้างต้น จะหน้าตาเหมือนการ์ดที่ออกแบบไว้ในต้นแบบ:

ตัวอย่างที่เรนเดอร์จริง (HTML/CSS)
🐕
น้องดำหาย
หายที่ ซอย 5 · เมื่อวานนี้
🔑 จุดที่ต้องเข้าใจ
การ์ดที่เห็นด้านบนนี้คือ HTML/CSS จริงที่ทำงานในเบราว์เซอร์ ไม่ใช่ภาพ — สังเกตว่าปุ่ม “ส่งเบาะแส” กดได้และมีเอฟเฟกต์ตอนชี้เมาส์ นี่คือความต่างระหว่าง “ต้นแบบ” กับ “เว็บจริง”

3.4 เพิ่มการโต้ตอบและรองรับหลายขนาดจอ

ขั้นสุดท้ายคือทำให้หน้าเว็บ “ตอบสนอง” ด้วย JavaScript (เช่น ตรวจฟอร์ม แสดงสถานะ loading/success) และ “ปรับตามขนาดจอ” (responsive) ด้วย CSS media query ซึ่งจะลงลึกในวิชาการพัฒนาเว็บแอปพลิเคชัน บทนี้ให้เห็นภาพการเชื่อมต่อ

// ตัวอย่างการโต้ตอบ: กดปุ่มแล้วแสดงสถานะ (เทียบกับ hotspot ในต้นแบบ)
const btn = document.querySelector('.btn--primary');
btn.addEventListener('click', () => {
  showState('loading');              // สถานะกำลังส่ง
  submitTip().then(() => showState('success'));  // สำเร็จ
});
/* responsive: มือถือ 1 คอลัมน์ จอใหญ่ 3 คอลัมน์ */
.post-grid { display:grid; grid-template-columns:1fr; gap:16px; }
@media (min-width:768px) {
  .post-grid { grid-template-columns:repeat(3, 1fr); }
}

4. สรุปท้ายบท

  • ต้นแบบมี 3 ระดับ: Lo-fi (wireframe), Mid-fi (mockup), Hi-fi (prototype) — เลือกตามวัตถุประสงค์และช่วงงาน
  • Interactive prototype เชื่อมหน้าจอด้วย hotspot เพื่อจำลอง user flow และทดสอบโดยยังไม่ต้องเขียนโค้ด
  • ต้องออกแบบ สถานะของหน้าจอ ให้ครบ: empty, loading, error, success
  • Design Handoff ส่งมอบ specs, design tokens, assets, states และ flow ให้นักพัฒนา
  • แปลงต้นแบบเป็นเว็บจริง: โครงสร้าง→HTML, จัดวาง→CSS Layout, สี/ตัวอักษร→CSS tokens, โต้ตอบ→JavaScript, รองรับหลายจอ→responsive
❓

5. คำถามทบทวน (ไม่เก็บคะแนน)

Lo-fi, Mid-fi และ Hi-fi ต่างกันอย่างไร และควรใช้ระดับใดในช่วงต้นของงาน เพราะเหตุใด
hotspot ในต้นแบบทำหน้าที่อะไร และเชื่อมโยงกับ User Flow จากบทที่ 6 อย่างไร
เหตุใดจึงต้องออกแบบสถานะ empty/loading/error ไม่ใช่แค่สถานะปกติ
Design Handoff ควรส่งมอบอะไรบ้างให้นักพัฒนา
จงจับคู่: การจัดวาง, สี/ตัวอักษร, การเชื่อมหน้า และการโต้ตอบ ไปยังเทคโนโลยีเว็บที่เกี่ยวข้อง
เหตุใด prototype จึงยังไม่ใช่ “เว็บจริง” และต้องผ่านกระบวนการใดจึงจะกลายเป็นเว็บที่ใช้งานได้

    เชื่อมหน้าจอด้วย hotspot ตาม user flow “แจ้งสัตว์หาย” ให้กดทดลองได้
📅 สัปดาห์ที่ 13 — สถานะหน้าจอ + แปลงเป็นโค้ด
  1. ออกแบบสถานะหน้าจอ (25 นาที)
    เพิ่มสถานะ empty/loading/error/success ให้หน้าจอสำคัญ
  2. เรียนรู้ Design Handoff (20 นาที)
    ดูการสาธิต แล้วลองเปิดดู specs/tokens และส่งออก assets จาก Figma ด้วยตนเอง
  3. แปลง 1 องค์ประกอบเป็นโค้ด (40 นาที)
    เลือก 1 องค์ประกอบ (เช่น การ์ดประกาศหรือปุ่ม) เขียน HTML/CSS ให้เหมือนต้นแบบ
  4. Peer Review & สรุป (15 นาที)
    เทียบโค้ดที่ได้กับต้นแบบ และเตรียมต้นแบบสำหรับทดสอบในบทที่ 10
📤

7. งานที่ต้องส่ง (Assignment 9)

⏰ กำหนดส่ง: ก่อนเริ่มคาบสัปดาห์ที่ 14

ชิ้นงาน: “Interactive Prototype + ตัวอย่างโค้ด 1 องค์ประกอบ”

เป็นชิ้นงานชิ้นที่ 9 ของ Design Portfolio ส่งเป็นไฟล์ PDF + ลิงก์ prototype + ไฟล์โค้ด ประกอบด้วย:

  1. Wireframe ของหน้าจอหลักอย่างน้อย 4 หน้า
  2. Hi-fi Prototype ที่กดได้ เชื่อม flow “แจ้งสัตว์หาย” ครบ (แนบลิงก์/ภาพ)
  3. สถานะหน้าจอ อย่างน้อย 3 สถานะ (เช่น empty, loading/error, success)
  4. ตัวอย่างโค้ดจริง ของ 1 องค์ประกอบ (HTML + CSS ที่ใช้ design tokens) พร้อมภาพผลลัพธ์ที่เรนเดอร์
  5. หมายเหตุ Handoff ระบุ spacing/สี/ฟอนต์ที่ใช้ และ assets ที่ต้องส่งมอบ
  6. สะท้อนคิด (Reflection) 3–5 บรรทัด: ความต่างระหว่างต้นแบบกับเว็บจริงที่ได้เรียนรู้

เกณฑ์ประเมิน: ความสมบูรณ์ของ prototype/flow (30%) · ความครบของสถานะหน้าจอ (20%) · คุณภาพโค้ดที่ตรงกับต้นแบบ (30%) · Handoff & สะท้อนคิด (20%)
