1. บทนำ

“ลองนึกถึงครั้งล่าสุดที่คุณกดปุ่มผิดบนแอป หรือหาปุ่มยกเลิกไม่เจอจนต้องปิดทั้งหน้า — ความหงุดหงิดนั้นเกิดจากความผิดของคุณ หรือเกิดจากการออกแบบที่ไม่ได้คำนึงถึงคุณ?”

ทุกวันนี้เราใช้ชีวิตอยู่ท่ามกลางหน้าจอ ตั้งแต่ตู้กดบัตรคิวในโรงพยาบาล แอปสั่งอาหาร ไปจนถึงระบบลงทะเบียนเรียน สิ่งเหล่านี้คือ “ระบบเชิงโต้ตอบ” (interactive system) ที่มนุษย์ต้องสื่อสารด้วยตลอดเวลา เมื่อระบบออกแบบมาดี เราจะใช้งานได้ลื่นไหลจนแทบไม่รู้ตัว แต่เมื่อออกแบบมาไม่ดี เราจะรู้สึกสับสน เสียเวลา หรือถึงขั้นทำงานผิดพลาด

วิชา การออกแบบประสบการณ์และส่วนติดต่อผู้ใช้ ศึกษาว่าจะทำอย่างไรให้ระบบที่เราสร้างขึ้น “เข้าใจง่ายและใช้งานได้จริง” สำหรับมนุษย์ บทแรกนี้จึงเป็นการวางรากฐานทางความคิด ก่อนที่บทต่อ ๆ ไปจะพาเราลงมือทำตั้งแต่การวิจัยผู้ใช้จนถึงการสร้างต้นแบบ

💭 ชวนคิดก่อนเริ่ม
หากนักศึกษาต้องสร้าง “เว็บแอปช่วยตามหาสัตว์เลี้ยงที่หายไป” คนที่กำลังเครียดเพราะสุนัขหายตั้งแต่เมื่อคืน เขาต้องการอะไรจากแอปของเรามากที่สุดในวินาทีแรกที่เปิดเข้ามา? นี่คือคำถามที่ UX พยายามตอบ

2. เนื้อหาหลัก

2.1 HCI คืออะไร

Human-Computer Interaction (HCI) หรือ “ปฏิสัมพันธ์ระหว่างมนุษย์และคอมพิวเตอร์” เป็นสาขาวิชาที่ศึกษาการออกแบบ การประเมิน และการนำไปใช้ของระบบคอมพิวเตอร์เชิงโต้ตอบ เพื่อให้มนุษย์ใช้งานได้อย่างมีประสิทธิภาพ HCI เป็นศาสตร์สหวิทยาการ (interdisciplinary) ที่ผสานความรู้จากวิทยาการคอมพิวเตอร์ จิตวิทยาการรับรู้ (cognitive psychology) การออกแบบ และการยศาสตร์ (ergonomics)

หัวใจของ HCI คือวงจรการสื่อสารระหว่างสามองค์ประกอบ ได้แก่ มนุษย์ (Human) ที่มีเป้าหมายในใจ ส่วนติดต่อ (Interface) ที่เป็นตัวกลาง และ ระบบ/คอมพิวเตอร์ (Computer) ที่ประมวลผล โดยมนุษย์ส่ง “คำสั่ง” (input) ผ่านส่วนติดต่อ และระบบตอบกลับด้วย “ผลลัพธ์” (feedback) เป็นวงจรต่อเนื่อง

กรณีศึกษา: แอปค้นหาสัตว์เลี้ยงหาย

เมื่อเจ้าของกดปุ่ม “แจ้งสัตว์เลี้ยงหาย” (input) ส่วนติดต่อจะแสดงฟอร์มกรอกข้อมูล ระบบบันทึกข้อมูลและแสดงข้อความ “แจ้งสำเร็จ พร้อมกระจายประกาศไปยังพื้นที่ใกล้เคียง” (feedback) ถ้าไม่มี feedback นี้ ผู้ใช้จะไม่แน่ใจว่าระบบทำงานหรือไม่ และอาจกดซ้ำหลายครั้ง

2.2 UX — ประสบการณ์ผู้ใช้ คืออะไร

User Experience (UX) คือ “ประสบการณ์โดยรวม” ที่ผู้ใช้รู้สึกและพบเจอตลอดการมีปฏิสัมพันธ์กับผลิตภัณฑ์หรือบริการ ไม่ใช่แค่ตอนกดหน้าจอ แต่รวมถึงความรู้สึกก่อนใช้ (ค้นเจอแอปได้ง่ายไหม) ระหว่างใช้ (ทำงานสำเร็จไหม เครียดไหม) และหลังใช้ (ประทับใจจนอยากกลับมาใช้อีกไหม) UX จึงครอบคลุมทั้งความมีประโยชน์ (useful) ความใช้งานง่าย (usable) และความน่าพึงพอใจ (desirable)

UX ไม่ได้เกิดจากหน้าจอเพียงอย่างเดียว แต่เป็นผลรวมของการวิจัยผู้ใช้ การจัดโครงสร้างข้อมูล การออกแบบการไหลของงาน และอารมณ์ความรู้สึก เปรียบได้กับ “ภูเขาน้ำแข็ง” ที่ UI เป็นส่วนที่มองเห็นเหนือผิวน้ำ ขณะที่งาน UX ส่วนใหญ่อยู่ใต้น้ำที่ผู้ใช้ไม่เห็นแต่สัมผัสได้

2.3 ตัวอย่าง: แอปเดียวกัน “UX ดี” กับ “UX ไม่ดี” ต่างกันอย่างไร

เพื่อให้เห็นภาพว่า UX ที่ดีคืออะไร ลองเทียบ “แอปค้นหาสัตว์เลี้ยงหาย” สองเวอร์ชันที่ มีฟีเจอร์เหมือนกัน แต่ออกแบบต่างกัน ในภารกิจเดียวกันคือ “เจ้าของเพิ่งรู้ว่าน้องหมาหลุดออกจากบ้าน ต้องแจ้งหายให้เร็วที่สุด”

แม้ทั้งสองแอปจะทำงาน “แจ้งหาย” ได้เหมือนกัน แต่ประสบการณ์ที่ผู้ใช้ได้รับต่างกันมาก ดังตารางเปรียบเทียบ

ประเด็น❌ แอปที่ UX ไม่ดี✓ แอปที่ UX ดี
ทำภารกิจสำเร็จ (success rate)หลายคนสับสนและล้มเลิกกลางคันเกือบทุกคนแจ้งหายสำเร็จ
เวลาที่ใช้~8 นาที (หาปุ่ม + กรอก 15 ช่อง)~45 วินาที (3 ช่อง)
ข้อผิดพลาดกดผิด กรอกผิด ส่งซ้ำหลายอันระบบเตือนก่อนพลาด แทบไม่ผิด
ความรู้สึกเครียด/หงุดหงิดซ้ำบนความตกใจอุ่นใจ รู้ว่าระบบช่วยจริง
ผลต่อเป้าหมายจริงข่าวกระจายช้า โอกาสเจอน้องหมาลดลงข่าวถึงคนใกล้เคียงทันที โอกาสเจอสูงขึ้น
ผลต่อผลิตภัณฑ์คนเลิกใช้ บอกต่อในแง่ลบคนกลับมาใช้ บอกต่อ แอปเติบโต
🔑 จุดที่ต้องเข้าใจ
ทั้งสองแอปมีฟีเจอร์เหมือนกันและหน้าตาอาจสวยพอ ๆ กัน (นั่นคือเรื่อง UI) แต่ UX ต่างกันเพราะ “ผู้ใช้ทำงานสำเร็จตามเป้าหมายจริงได้ไหม และรู้สึกอย่างไรตลอดทาง” — UX ที่ดีไม่ได้ มีของมากกว่า แต่ เข้าใจว่าผู้ใช้ต้องการอะไรในบริบทนั้น แล้วตัดสิ่งที่ไม่จำเป็นออก ซึ่งเริ่มจากการวิจัยผู้ใช้ ไม่ใช่การเดาแล้วรีบออกแบบหน้าจอ

2.4 UI — ส่วนติดต่อผู้ใช้ คืออะไร

User Interface (UI) คือจุดที่มนุษย์ “สัมผัส” กับระบบโดยตรง ได้แก่สิ่งที่มองเห็นและโต้ตอบได้บนหน้าจอ เช่น ปุ่ม เมนู ฟอร์ม ไอคอน สี ตัวอักษร และการจัดวาง UI เป็นเรื่องของการสื่อสารด้วยภาพ (visual) และการโต้ตอบ (interaction) ที่ทำให้แนวคิด UX ที่ออกแบบไว้ กลายเป็นสิ่งที่ผู้ใช้จับต้องได้จริง

🔑 จุดที่ต้องเข้าใจ
UI ที่สวยงามแต่สับสน ไม่นับเป็น UX ที่ดี และในทางกลับกัน UX ที่วางแผนดีแต่ UI ทำออกมาไม่ชัดเจน ผู้ใช้ก็จะไม่ได้รับประสบการณ์ตามที่ตั้งใจ ทั้งสองด้านต้องทำงานร่วมกัน

2.5 ความแตกต่างระหว่าง UX กับ UI

นักศึกษาจำนวนมากสับสนระหว่างสองคำนี้ วิธีจำที่ง่ายที่สุดคือ UX = “รู้สึกอย่างไร” (how it works / feels) ส่วน UI = “หน้าตาเป็นอย่างไร” (how it looks) ภาพด้านล่างเปรียบเทียบทั้งสองในรูปแบบภูเขาน้ำแข็ง

ประเด็นUX (User Experience)UI (User Interface)
คำถามหลักใช้แล้วรู้สึก/ทำงานสำเร็จอย่างไรหน้าตาและการโต้ตอบเป็นอย่างไร
เน้นเรื่องกระบวนการ การวิจัย โครงสร้าง อารมณ์ภาพ สี ตัวอักษร การจัดวาง องค์ประกอบ
ผลงานตัวอย่างPersona, Journey Map, User Flow, WireframeStyle guide, Mockup, Visual design, Prototype
คำถามวัดผลผู้ใช้บรรลุเป้าหมายได้ไหมผู้ใช้รู้ว่าต้องกดอะไรหรือไม่
เปรียบเทียบโครงสร้างและการวางผังของบ้านสีผนัง เฟอร์นิเจอร์ การตกแต่ง
⚠️ ข้อผิดพลาดที่พบบ่อย
  • คิดว่า “UX = ทำให้สวย” — จริง ๆ แล้วความสวยเป็นส่วนหนึ่งของ UI ส่วน UX เน้นว่าผู้ใช้ทำงานสำเร็จและรู้สึกดีหรือไม่
  • เริ่มออกแบบหน้าจอ (UI) ทันทีโดยข้ามขั้นวิจัยผู้ใช้ (UX) ทำให้ได้แอปสวยที่ไม่มีใครอยากใช้
  • ใช้คำว่า UX/UI สลับกันโดยไม่แยกแยะ ทำให้สื่อสารกับทีมพัฒนาคลาดเคลื่อน
กรณีศึกษา: แอปค้นหาสัตว์เลี้ยงหาย

งาน UX: ค้นพบว่าเจ้าของที่กำลังตกใจต้องการ “แจ้งหายให้เร็วที่สุด” จึงออกแบบให้ปุ่มแจ้งหายอยู่หน้าแรก กรอกข้อมูลน้อยที่สุด   งาน UI: ทำปุ่ม “แจ้งสัตว์เลี้ยงหาย” เป็นสีแดงส้มขนาดใหญ่ ตัวอักษรชัด มองเห็นทันทีที่เปิดแอป

2.6 Usability — ความสามารถในการใช้งานได้

Usability คือระดับที่ผู้ใช้สามารถใช้ระบบเพื่อบรรลุเป้าหมายได้อย่างมีประสิทธิผล (effective) มีประสิทธิภาพ (efficient) และพึงพอใจ (satisfying) Jakob Nielsen ผู้เชี่ยวชาญด้าน usability ได้แบ่งองค์ประกอบของ usability ออกเป็น 5 ด้าน

ทั้ง 5 องค์ประกอบมีความหมายดังนี้

  • Learnability (ความง่ายในการเรียนรู้): ผู้ใช้ใหม่ที่ไม่เคยใช้ระบบมาก่อน สามารถเรียนรู้วิธีทำงานพื้นฐานได้ง่ายและรวดเร็วเพียงใดในการใช้งานครั้งแรก
  • Efficiency (ประสิทธิภาพในการใช้งาน): เมื่อผู้ใช้เรียนรู้ระบบแล้ว สามารถทำงานให้สำเร็จได้รวดเร็วเพียงใดในการใช้งานครั้งถัด ๆ ไป
  • Memorability (ความน่าจดจำ): เมื่อผู้ใช้กลับมาใช้ระบบอีกครั้งหลังจากไม่ได้ใช้งานเป็นระยะเวลาหนึ่ง สามารถจำวิธีใช้งานเดิมได้ง่ายเพียงใด โดยไม่ต้องเรียนรู้ใหม่ตั้งแต่ต้น
  • Errors (ข้อผิดพลาด): ระบบช่วยป้องกันไม่ให้ผู้ใช้เกิดข้อผิดพลาดได้มากน้อยเพียงใด และเมื่อเกิดข้อผิดพลาดขึ้นแล้ว ผู้ใช้สามารถแก้ไขหรือกู้คืนสู่สถานะปกติได้ง่ายเพียงใด
  • Satisfaction (ความพึงพอใจ): ผู้ใช้รู้สึกพึงพอใจ สบายใจ และเพลิดเพลินกับการใช้งานระบบมากน้อยเพียงใด
กรณีศึกษา: แอปค้นหาสัตว์เลี้ยงหาย
  • Learnability: ผู้ใช้ครั้งแรกแจ้งสัตว์หายได้สำเร็จโดยไม่ต้องอ่านคู่มือ
  • Efficiency: แจ้งหายเสร็จภายใน 3 ขั้นตอน
  • Memorability: เจ้าของที่เคยแจ้งหายไว้เมื่อหลายเดือนก่อน กลับมาเปิดแอปอีกครั้งเมื่อสัตว์เลี้ยงอีกตัวหาย ก็ยังกดปุ่ม “🐾 แจ้งสัตว์หาย” ได้ถูกต้องทันทีโดยไม่ต้องนึกหรือค้นหาเมนู
  • Errors: ถ้ากรอกเบอร์ติดต่อผิดรูปแบบ ระบบเตือนทันทีก่อนส่ง
  • Satisfaction: หลังกดแจ้งหายสำเร็จ ระบบแสดงข้อความ “✓ แจ้งสำเร็จ · กระจายข่าวแล้ว” พร้อมโทนสีเขียวที่ให้ความรู้สึกอุ่นใจ ทำให้เจ้าของรู้สึกว่ามีคนช่วยตามหาจริง ๆ ในยามที่กำลังกังวล

2.7 การออกแบบที่ยึดผู้ใช้เป็นศูนย์กลาง และ Mental Model

User-Centered Design (UCD) คือปรัชญาการออกแบบที่ให้ความต้องการและข้อจำกัดของผู้ใช้เป็นตัวตั้งในทุกขั้นตอนการตัดสินใจ แทนที่จะออกแบบตามความชอบของนักออกแบบหรือความสะดวกของระบบ UCD เป็นกระบวนการวนซ้ำ (iterative) ที่ประกอบด้วยการเข้าใจบริบทผู้ใช้ → ระบุความต้องการ → ออกแบบทางแก้ → ประเมินกับผู้ใช้จริง แล้ววนกลับไปปรับปรุง

Mental Model (แบบจำลองทางความคิด) คือความเข้าใจที่ผู้ใช้มีอยู่ในหัวว่าระบบ “น่าจะทำงานอย่างไร” จากประสบการณ์เดิม เช่น ผู้ใช้คาดว่ารูปไอคอนถังขยะคือการลบ หรือไอคอนแว่นขยายคือการค้นหา การออกแบบที่ดีควรสอดคล้องกับ mental model ของผู้ใช้ เพื่อให้ใช้งานได้ทันทีโดยไม่ต้องเรียนรู้ใหม่

⚠️ ข้อผิดพลาดที่พบบ่อย
ออกแบบไอคอนหรือคำที่ “สร้างสรรค์เกินไป” จนขัดกับ mental model ของผู้ใช้ เช่น ใช้รูปดอกไม้แทนปุ่มค้นหา ผู้ใช้จะหาไม่เจอและสับสน — ความแปลกใหม่ที่ดีต้องไม่แลกกับความเข้าใจง่าย

2.8 Problem Statement คืออะไร

Problem Statement (ประโยคระบุปัญหา) คือประโยคสั้น ๆ ที่สรุปปัญหาของผู้ใช้อย่างชัดเจนและยึดผู้ใช้เป็นศูนย์กลาง เป็นผลลัพธ์ชิ้นแรกของกระบวนการออกแบบที่ดี เพราะช่วยให้ทีมงานทั้งหมด — ทั้งนักออกแบบและนักพัฒนา — โฟกัสไปที่ “ปัญหาที่แท้จริงของผู้ใช้” ก่อนที่จะรีบกระโดดไปคิดฟีเจอร์หรือลงมือออกแบบหน้าจอ ซึ่งเป็นความเสี่ยงที่กล่าวถึงในหัวข้อ 2.5

โครงสร้างของ Problem Statement ที่นิยมใช้ในกระบวนการ UX มีรูปแบบดังนี้

📝 รูปแบบ Problem Statement
“[ผู้ใช้] ต้องการ [เป้าหมาย] แต่ [อุปสรรค] ทำให้ [ผลกระทบ]”

แต่ละส่วนของประโยคมีความหมายดังนี้

  • [ผู้ใช้] — ระบุกลุ่มผู้ใช้ให้เจาะจง ไม่ใช้คำกว้าง ๆ เช่น “ผู้ใช้ทุกคน” แต่ควรระบุบริบทหรือลักษณะเฉพาะ เช่น “เจ้าของสัตว์เลี้ยงที่เพิ่งพบว่าสัตว์หาย”
  • [เป้าหมาย] — สิ่งที่ผู้ใช้ต้องการบรรลุ ต้องเป็น เป้าหมาย ไม่ใช่ ทางแก้ปัญหา (solution) เช่น “แจ้งเตือนคนใกล้เคียงให้เร็วที่สุด” ไม่ใช่ “อยากได้ปุ่มสีแดง”
  • [อุปสรรค] — สิ่งที่ขัดขวางไม่ให้ผู้ใช้บรรลุเป้าหมายได้ในปัจจุบัน ควรมาจากข้อมูลจริงหรือการสังเกต ไม่ใช่การคาดเดา
  • [ผลกระทบ] — ผลลัพธ์เชิงลบที่เกิดขึ้นจากอุปสรรคนั้น ยิ่งระบุให้วัดผลได้ (เช่น เวลาที่เสียไป โอกาสที่พลาด) ยิ่งช่วยให้ประเมินความสำเร็จของการออกแบบในภายหลังได้ง่าย
⚠️ ข้อผิดพลาดที่พบบ่อยในการเขียน Problem Statement
  • เขียนเป็น solution/feature แทนที่จะเป็นปัญหา เช่น “ผู้ใช้ต้องการปุ่มสั่งซื้อด่วนสีแดง” — นี่คือทางแก้ ไม่ใช่ปัญหา
  • ระบุผู้ใช้กว้างเกินไปจนไม่มีบริบท เช่น “ผู้ใช้ทุกคนต้องการแอปที่ดี”
  • ไม่มีอุปสรรคหรือผลกระทบที่ชัดเจน ทำให้ไม่รู้ว่าจะออกแบบเพื่อแก้อะไร และวัดผลความสำเร็จไม่ได้

ตารางต่อไปนี้เปรียบเทียบตัวอย่าง Problem Statement ที่ เขียนถูกต้อง กับที่ เขียนไม่ถูกต้อง จากแอปพลิเคชัน 5 ประเภทที่พบได้ทั่วไป

แอปพลิเคชัน✓ ตัวอย่างที่ถูกต้อง✗ ตัวอย่างที่ไม่ถูกต้อง
1. แอปสั่งอาหารเดลิเวอรี พนักงานออฟฟิศที่มีเวลาพักเที่ยงจำกัด ต้องการสั่งอาหารให้มาถึงทันภายในเวลาพัก แต่ขั้นตอนเลือกเมนูในแอปซับซ้อนและใช้เวลานาน ทำให้พลาดเวลาพักหรือต้องรีบกินอาหารอย่างเร่งรีบ “ผู้ใช้ต้องการปุ่มสั่งซื้อด่วนสีแดงตรงกลางหน้าจอ” — ระบุ ทางแก้ (solution) ไม่ใช่ปัญหาของผู้ใช้
2. แอปธนาคารบนมือถือ ผู้สูงอายุที่ไม่ถนัดเทคโนโลยี ต้องการโอนเงินให้ลูกหลานได้ด้วยตนเอง แต่ขั้นตอนยืนยันตัวตนมีศัพท์เทคนิคและหลายขั้นตอนเกินไป ทำให้ต้องพึ่งพาคนอื่นทำแทนอยู่เสมอและรู้สึกไม่มั่นใจในตัวเอง “ผู้ใช้ทุกคนต้องการแอปธนาคารที่ทันสมัยและสวยงาม” — ไม่ระบุกลุ่มผู้ใช้ที่ชัดเจน และไม่มีอุปสรรค/ผลกระทบที่วัดผลได้
3. แพลตฟอร์มเรียนออนไลน์ นักศึกษาที่เรียนออนไลน์นอกเวลางาน ต้องการติดตามบทเรียนที่เรียนค้างไว้ให้ต่อได้ทันที แต่ระบบไม่บันทึกจุดที่หยุดดูวิดีโอไว้ ทำให้ต้องเสียเวลาไล่หาบทเรียนเดิมทุกครั้งจนหมดกำลังใจเรียนต่อ “ระบบควรมี Dashboard แสดงกราฟความคืบหน้าที่สวยงาม” — เป็นข้อเสนอฟีเจอร์ ไม่ใช่การนิยามปัญหา
4. แอปจองคิวโรงพยาบาล ผู้ป่วยโรคเรื้อรังที่ต้องมาพบแพทย์เป็นประจำ ต้องการทราบเวลาที่ต้องรอคิวจริงล่วงหน้า แต่แอปแสดงเพียงหมายเลขคิวโดยไม่ระบุเวลาโดยประมาณ ทำให้ต้องนั่งรอที่โรงพยาบาลนานเกินความจำเป็น “ผู้ป่วยรู้สึกหงุดหงิดกับโรงพยาบาล” — คลุมเครือเกินไป ไม่ระบุเป้าหมาย อุปสรรค หรือผลกระทบที่ชัดเจน
5. แอปค้นหาสัตว์เลี้ยงหาย (กรณีศึกษาหลัก) เจ้าของสัตว์เลี้ยงที่เพิ่งพบว่าสัตว์เลี้ยงหายไปจากบ้าน ต้องการแจ้งเตือนคนในพื้นที่ใกล้เคียงให้เร็วที่สุด แต่แอปที่มีอยู่ต้องกรอกฟอร์มยาวและหาปุ่มแจ้งหายยาก ทำให้แจ้งข่าวได้ช้าและโอกาสตามหาสัตว์เลี้ยงเจอลดลง “อยากให้มีแอปค้นหาสัตว์เลี้ยงหายที่ใช้ AI จดจำใบหน้าสัตว์” — เป็นการเสนอฟีเจอร์/เทคโนโลยี ไม่ใช่การนิยามปัญหาของผู้ใช้
🔑 จุดที่ต้องเข้าใจ
Problem Statement ที่ดีไม่ได้บอกว่า “จะสร้างอะไร” แต่บอกว่า “ใครมีปัญหาอะไร และปัญหานั้นส่งผลอย่างไร” ยิ่งเขียนได้เจาะจงและวัดผลได้มากเท่าไร ก็ยิ่งช่วยนำทางการออกแบบในบทถัดไป (Design Thinking, Persona, Journey Map) ให้ตรงจุดมากขึ้นเท่านั้น ในกิจกรรม Workshop ท้ายบทนี้ นักศึกษาจะได้ฝึกเขียน Problem Statement ของแอปค้นหาสัตว์เลี้ยงหายด้วยตนเอง โดยใช้รูปแบบและตัวอย่างข้างต้นเป็นแนวทาง

เชื่อมโยงสู่การพัฒนาเว็บ: UI ที่ดีเริ่มจากโครงสร้างที่สื่อความหมาย

แม้บทนี้จะเน้นแนวคิด แต่หลักการ UX/UI ส่งผลถึงการเขียนโค้ดโดยตรง ตัวอย่างปุ่ม “แจ้งสัตว์เลี้ยงหาย” ควรเขียนด้วย HTML ที่สื่อความหมาย (semantic) เพื่อให้ทั้งผู้ใช้ทั่วไปและผู้ใช้ screen reader เข้าใจตรงกัน — เป็นการเชื่อมโยงกับวิชาการพัฒนาเว็บแอปพลิเคชัน

3. สรุปท้ายบท

  • HCI คือศาสตร์สหวิทยาการที่ศึกษาปฏิสัมพันธ์ระหว่างมนุษย์ ส่วนติดต่อ และระบบ ผ่านวงจร input–feedback
  • UX คือประสบการณ์โดยรวมของผู้ใช้ (รู้สึก/ทำงานสำเร็จอย่างไร) ส่วน UI คือส่วนที่ผู้ใช้สัมผัสและมองเห็น (หน้าตาเป็นอย่างไร) ทั้งสองต้องทำงานร่วมกัน
  • Usability ประกอบด้วย 5 ด้าน: Learnability, Efficiency, Memorability, Errors, Satisfaction
  • User-Centered Design (UCD) เป็นกระบวนการวนซ้ำที่ยึดผู้ใช้เป็นศูนย์กลางในทุกการตัดสินใจ
  • Mental Model คือความคาดหวังของผู้ใช้ที่นักออกแบบควรออกแบบให้สอดคล้อง เพื่อให้ใช้งานได้ง่ายโดยไม่ต้องเรียนรู้ใหม่
❓

4. คำถามทบทวน (ไม่เก็บคะแนน)

จงอธิบายความหมายของ HCI ด้วยภาษาของตนเอง พร้อมระบุองค์ประกอบสามส่วนในวงจรปฏิสัมพันธ์
UX กับ UI ต่างกันอย่างไร? ยกตัวอย่างองค์ประกอบของแต่ละด้านมาอย่างละ 2 รายการจากแอปที่นักศึกษาใช้ประจำ
องค์ประกอบ 5 ด้านของ Usability ตาม Nielsen มีอะไรบ้าง และด้านใดที่นักศึกษาคิดว่าสำคัญที่สุดสำหรับแอปฉุกเฉิน เพราะเหตุใด
“Mental Model” มีผลต่อการเลือกใช้ไอคอนและคำในส่วนติดต่ออย่างไร ยกตัวอย่างไอคอนที่สอดคล้องและขัดแย้งกับ mental model
เหตุใดการเริ่มออกแบบ UI ทันทีโดยข้ามงาน UX จึงเป็นความเสี่ยง? อธิบายโดยเชื่อมโยงกับกรณีแอปค้นหาสัตว์เลี้ยงหาย

5. ขั้นตอน Workshop ในคาบ

กิจกรรมในคาบ (ปฏิบัติ 2 ชั่วโมง) ทำเป็นกลุ่มย่อย 3–4 คน โดยใช้กระดาษ/ไวต์บอร์ดหรือ FigJam/Miro ห้ามใช้เครื่องมือ AI

  1. วอร์มอัป: “แอปที่ฉันเกลียด” (10 นาที)
    แต่ละคนเล่าประสบการณ์ใช้แอป/เว็บที่ใช้งานยาก 1 ตัว แล้วระบุว่าเป็นปัญหาด้าน UX หรือ UI
  2. ทบทวนแนวคิดหลักร่วมกัน (15 นาที)
    ทบทวนแนวคิด HCI, UX vs UI, Usability และ mental model จดประเด็นสำคัญที่จะใช้ในกิจกรรม และซักถามข้อสงสัย
  3. ทำความรู้จักกรณีศึกษา (15 นาที)
    ทำความเข้าใจโจทย์ “เว็บแอปค้นหาสัตว์เลี้ยงหาย” แล้วอภิปรายในกลุ่มว่าใครคือผู้ใช้ และเขาเจอปัญหาอะไร
  4. ระดมสมองปัญหาของผู้ใช้ (25 นาที)
    เขียน sticky note ปัญหาที่เจ้าของสัตว์เลี้ยงและผู้พบเห็นน่าจะเจอ แล้วจัดกลุ่มปัญหาที่คล้ายกัน
  5. ร่าง Problem Statement (25 นาที)
    เขียนประโยคปัญหาในรูปแบบ: “[ผู้ใช้] ต้องการ [เป้าหมาย] แต่ [อุปสรรค] ทำให้ [ผลกระทบ]” — ทบทวนความหมายและตัวอย่างที่ถูก/ไม่ถูกต้องได้ที่หัวข้อ 2.8 Problem Statement คืออะไร ก่อนเริ่มเขียน
  6. Peer Review (20 นาที)
    สลับผลงานกับอีกกลุ่ม ให้ข้อเสนอแนะตามเกณฑ์: ปัญหาชัดเจนไหม / ยึดผู้ใช้เป็นศูนย์กลางไหม / วัดผลได้ไหม
  7. นำเสนอและสรุป (10 นาที)
    แต่ละกลุ่มนำเสนอ Problem Statement 1 ประโยค ร่วมกันสรุปบทเรียน และทบทวนโจทย์งานที่ต้องส่ง
📤

6. งานที่ต้องส่ง (Assignment 1)

⏰ กำหนดส่ง: ก่อนเริ่มคาบสัปดาห์ที่ 2

ชิ้นงาน: เอกสาร “Problem Statement & การวิเคราะห์ UX/UI เบื้องต้น”

เป็นชิ้นงานชิ้นแรกของ Design Portfolio สะสมตลอดวิชา ส่งเป็นไฟล์ PDF 1–2 หน้า ประกอบด้วย:

  1. Problem Statement ของแอปค้นหาสัตว์เลี้ยงหาย (ปรับปรุงจากที่ร่างในคาบ) เขียนตามรูปแบบ “ผู้ใช้–เป้าหมาย–อุปสรรค–ผลกระทบ”
  2. ระบุกลุ่มผู้ใช้หลัก อย่างน้อย 2 กลุ่ม (เช่น เจ้าของที่ทำสัตว์เลี้ยงหาย / ผู้พบเห็นสัตว์จร) พร้อมเป้าหมายของแต่ละกลุ่ม
  3. ตารางแยกประเด็น UX และ UI ของแอปนี้อย่างละ 3 ข้อ (เช่น UX: ต้องแจ้งหายได้เร็ว / UI: ปุ่มแจ้งหายต้องเด่น)
  4. วิเคราะห์ Usability โดยเลือก 2 จาก 5 ด้านของ Nielsen ที่สำคัญที่สุดสำหรับแอปนี้ พร้อมเหตุผล
  5. สะท้อนคิด (Reflection) 3–5 บรรทัด: บทเรียนสำคัญที่ได้จากบทนี้

เกณฑ์ประเมิน: ความชัดเจนของปัญหา (30%) · การยึดผู้ใช้เป็นศูนย์กลาง (25%) · ความถูกต้องของการแยก UX/UI (25%) · การวิเคราะห์ usability (20%)
