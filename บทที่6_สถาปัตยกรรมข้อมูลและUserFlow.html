“ถ้าห้องสมุดจัดหนังสือมั่ว ๆ ต่อให้มีหนังสือดีแค่ไหน ก็ไม่มีใครหาเจอ” — แอปก็เช่นกัน ถ้าเนื้อหาดีแต่จัดวางสับสน ผู้ใช้จะหาในสิ่งที่ต้องการไม่พบ แล้วเราจะ ‘จัดระเบียบ’ ให้ตรงกับวิธีคิดของผู้ใช้ได้อย่างไร?

ในบทที่ 5 เราค้นพบ “โอกาสในการออกแบบ” จาก journey map เช่น ฟอร์มแจ้งหายที่สั้น การรวมเบาะแสไว้ที่เดียว โอกาสเหล่านี้คือ “สิ่งที่แอปควรมี” แต่ยังเป็นรายการกระจัดกระจาย บทนี้จะนำมาจัดระเบียบให้เป็นโครงสร้างที่ชัดเจน ผ่านสองเครื่องมือ: Information Architecture (จัดเนื้อหาอยู่ที่ไหน) และ User Flow (ผู้ใช้เดินจากหน้าหนึ่งไปอีกหน้าอย่างไร)

2. เนื้อหาหลัก

2.1 Information Architecture คืออะไร

สถาปัตยกรรมข้อมูล (Information Architecture — IA) คือศาสตร์และศิลป์ของการจัดระเบียบ จัดโครงสร้าง และตั้งชื่อเนื้อหา เพื่อให้ผู้ใช้ค้นหาสิ่งที่ต้องการและเข้าใจว่าตนเองอยู่ที่ใดในระบบได้ง่าย IA ที่ดีจะสอดคล้องกับ mental model ของผู้ใช้ (จากบทที่ 1) องค์ประกอบหลักของ IA ได้แก่ ระบบการจัดระเบียบ (organization), ระบบการตั้งชื่อ (labeling), ระบบนำทาง (navigation) และระบบค้นหา (search)

2.2 Card Sorting — จัดกลุ่มตามวิธีคิดของผู้ใช้

Card Sorting เป็นเทคนิคให้ผู้ใช้จัดกลุ่ม “การ์ด” ที่เขียนชื่อเนื้อหา/ฟีเจอร์ลงไป เพื่อค้นหาว่าผู้ใช้คาดหวังให้สิ่งเหล่านั้นถูกจัดกลุ่มอย่างไร แบ่งเป็น Open card sorting (ผู้ใช้ตั้งชื่อกลุ่มเอง) และ Closed card sorting (กำหนดกลุ่มไว้ให้แล้ว ผู้ใช้แค่จัดของลงกลุ่ม)

“การ์ดเนื้อหา” คืออะไร และควรเขียนชื่ออะไรลงไป

การ์ดเนื้อหา (content card) แต่ละใบแทน หนึ่งหน่วยเนื้อหาหรือหนึ่งฟังก์ชัน ของระบบ — อาจเป็น “หน้าจอ”, “เนื้อหา/ข้อมูลที่ผู้ใช้ต้องการ” หรือ “การกระทำที่ผู้ใช้ทำได้” การ์ดเหล่านี้รวบรวมมาจาก 3 แหล่งหลัก: โอกาสในการออกแบบจาก journey map (บทที่ 5), ฟีเจอร์ที่ระบบจำเป็นต้องมี, และเนื้อหาที่ผู้ใช้คาดหวังจะเจอ การเขียนชื่อบนการ์ดให้ดีสำคัญมาก เพราะถ้าชื่อกำกวม ผลการจัดกลุ่มก็จะเชื่อถือไม่ได้

หลักการเขียนชื่อบนการ์ดเนื้อหามี 6 ข้อ:

  1. หนึ่งการ์ดหนึ่งความคิด (one concept per card) — ห้ามรวมหลายเรื่องในใบเดียว เช่น อย่าเขียน “แจ้งหายและแจ้งพบ” ให้แยกเป็น 2 ใบ
  2. ใช้คำของผู้ใช้ ไม่ใช่ศัพท์เทคนิคหรือศัพท์ภายในองค์กร — เช่น ใช้ “แจ้งสัตว์เลี้ยงหาย” แทน “สร้าง Lost-Pet Record”
  3. ระดับความละเอียดสม่ำเสมอ (consistent granularity) — อย่าปนหัวข้อใหญ่ (เช่น “โปรไฟล์”) กับรายละเอียดเล็กมาก (เช่น “เปลี่ยนรูปโปรไฟล์”) ไว้ในชุดเดียวกัน
  4. ใช้คำนามสำหรับเนื้อหา/หน้า และคำกริยาสำหรับการกระทำ — เช่น เนื้อหา: “รายละเอียดประกาศ” (คำนาม) ส่วนการกระทำ: “ส่งเบาะแส” (คำกริยา)
  5. ชื่อชัดเจนเข้าใจได้ทันที โดยไม่ต้องอธิบายเพิ่ม — หลีกเลี่ยงคำกำกวมอย่าง “จัดการ” หรือ “อื่น ๆ”
  6. หลีกเลี่ยงคำย่อและชื่อแบรนด์เฉพาะ ที่ผู้เข้าร่วมอาจไม่คุ้นเคย
❌ ชื่อการ์ดที่ไม่ดี✅ ปรับให้ดีขึ้นเหตุผล
จัดการสัตว์เลี้ยงประกาศของฉัน“จัดการ” กำกวม ไม่บอกว่าทำอะไร
โมดูลแจ้งเตือน (Noti Module)การแจ้งเตือนเมื่อมีสัตว์หายใกล้ฉันเลี่ยงศัพท์เทคนิค ใช้ภาษาผู้ใช้
แจ้งหาย + แนบรูป + เลือกพิกัดแจ้งสัตว์เลี้ยงหายหนึ่งการ์ดควรมีหนึ่งความคิด
ข้อมูลรายละเอียดประกาศสัตว์หายเจาะจงพอที่จะจัดกลุ่มได้

2.3 ตัวอย่างชุดการ์ดเนื้อหา และการจัดกลุ่มตามวิธีคิดผู้ใช้

หัวข้อนี้แยกออกมาเป็นการเฉพาะ เพราะเป็นขั้นที่ลงรายละเอียดมากและเป็น “หัวใจ” ที่เชื่อมจากการรวบรวมการ์ด ไปสู่การได้โครงสร้าง (Sitemap) ในหัวข้อถัดไป เราจะเริ่มจากชุดการ์ดตั้งต้น แล้วดูว่าเมื่อให้ผู้ใช้จัดกลุ่ม (open card sorting) ผลลัพธ์จะออกมาอย่างไร และเหตุใดจึงตั้งชื่อกลุ่มเช่นนั้น

ก. ชุดการ์ดเนื้อหาตั้งต้น (ก่อนจัดกลุ่ม)

ด้านล่างเป็นชุดการ์ดตัวอย่างที่นักศึกษานำไปใช้ทำ card sorting ได้จริง โดยแยกสีระหว่าง “เนื้อหา/หน้า” (คำนาม) กับ “การกระทำ/ฟังก์ชัน” (คำกริยา)

เนื้อหา/หน้า (คำนาม) การกระทำ/ฟังก์ชัน (คำกริยา)
แจ้งสัตว์เลี้ยงหาย แจ้งพบสัตว์จร ประกาศสัตว์หายทั้งหมด ค้นหาตามพื้นที่ กรองตามประเภทสัตว์ รายละเอียดประกาศ รูปภาพสัตว์ แผนที่จุดพบเห็นล่าสุด ส่งเบาะแส แชตกับเจ้าของ โทรหาเจ้าของ การแจ้งเตือนสัตว์หายใกล้ฉัน ตั้งค่ารัศมีแจ้งเตือน ประกาศของฉัน แก้ไขประกาศ ปิดประกาศ (เจอแล้ว) โปรไฟล์ผู้ใช้ แก้ไขข้อมูลส่วนตัว เข้าสู่ระบบ สมัครสมาชิก ประวัติการแจ้ง บันทึก/ติดตามประกาศ แชร์ประกาศไปโซเชียล รายงานประกาศไม่เหมาะสม คำถามที่พบบ่อย (FAQ) ติดต่อทีมงาน
🔑 จุดที่ต้องเข้าใจ
จำนวนการ์ดที่เหมาะสมสำหรับระบบขนาดกลางอยู่ที่ราว 30–60 ใบ — น้อยเกินไปจะได้ข้อมูลไม่พอ มากเกินไปจะทำให้ผู้เข้าร่วมเหนื่อยล้าและจัดกลุ่มไม่รอบคอบ

ข. ผลการจัดกลุ่มตามวิธีคิดของผู้ใช้ (จาก Open Card Sorting)

เมื่อนำการ์ดทั้งหมดให้ผู้ใช้กลุ่มเป้าหมายช่วยจัดกลุ่ม ผลลัพธ์มักรวมตัวกันตาม “เป้าหมายหรืองาน” ที่ผู้ใช้คิดในใจ ไม่ใช่ตามโครงสร้างทางเทคนิค เราตั้งชื่อกลุ่มด้วยภาษาของผู้ใช้ และได้ 5 กลุ่มหลักดังนี้

1 แจ้งเรื่องสัตว์
ผู้ใช้มองว่าเป็น “การลงมือทำเมื่อมีเหตุ” — ทั้งของหายและพบเจอ จึงรวมไว้ด้วยกัน
แจ้งสัตว์เลี้ยงหายแจ้งพบสัตว์จร
2 ค้นหา/ดูประกาศ
ผู้ใช้คิดเป็น “การหาและดูข้อมูล” ไม่ว่าจะตามหาของตนเองหรือช่วยดูให้คนอื่น
ประกาศสัตว์หายทั้งหมดค้นหาตามพื้นที่กรองตามประเภทสัตว์รายละเอียดประกาศรูปภาพสัตว์แผนที่จุดพบเห็นล่าสุด
+ การกระทำในหน้ารายละเอียด: ส่งเบาะแส · แชต/โทรหาเจ้าของ · แชร์ · รายงานประกาศ
3 การแจ้งเตือน
ผู้ใช้แยก “สิ่งที่ระบบส่งมาหาเรา” ออกจากสิ่งที่เราไปหาเอง อย่างชัดเจน
การแจ้งเตือนสัตว์หายใกล้ฉันตั้งค่ารัศมีแจ้งเตือน
4 บัญชีของฉัน
ผู้ใช้รวมทุกอย่างที่ “เป็นของฉัน / ฉันจัดการเอง” ไว้ในที่เดียว
เข้าสู่ระบบสมัครสมาชิกโปรไฟล์ผู้ใช้แก้ไขข้อมูลส่วนตัวประกาศของฉันแก้ไขประกาศปิดประกาศ (เจอแล้ว)บันทึก/ติดตามประกาศประวัติการแจ้ง
5 ช่วยเหลือ
เนื้อหาสนับสนุนที่ไม่ใช่งานหลัก ผู้ใช้มักจัดไว้กลุ่มท้ายสุด
คำถามที่พบบ่อย (FAQ)ติดต่อทีมงาน

ค. ทำไมตั้งชื่อกลุ่มแบบนี้ และจะนำไปทำอะไรต่อ

ชื่อกลุ่มมาจาก “คำและเหตุผลที่ผู้ใช้ใช้จริง” ระหว่าง card sorting ไม่ใช่จากศัพท์เทคนิคของทีม กลุ่มเหล่านี้จะกลายเป็นเมนูหลัก (navigation) และโครงของ Sitemap ในขั้นถัดไป

กลุ่มทำไมตั้งชื่อนี้นำไปทำอะไรต่อ
1. แจ้งเรื่องสัตว์เป็นงานเร่งด่วนที่ผู้ใช้คิดถึงก่อนเมื่อมีเหตุเป็นปุ่ม/เมนูเด่นบนหน้าแรก เข้าถึงได้ใน 1 แตะ
2. ค้นหา/ดูประกาศเป็นพฤติกรรม “หาและดู” ที่ใช้บ่อยเป็นแท็บหลัก พร้อมหน้ารายละเอียดและตัวกรอง
3. การแจ้งเตือนเป็นข้อมูลที่ “วิ่งเข้าหาผู้ใช้” ต่างจากการค้นเองเป็นศูนย์การแจ้งเตือน + หน้าตั้งค่า
4. บัญชีของฉันรวมสิ่งที่ผู้ใช้เป็นเจ้าของและจัดการเองเป็นเมนูโปรไฟล์ รวมประกาศของฉันและการตั้งค่า
5. ช่วยเหลือเนื้อหาสนับสนุน ใช้ไม่บ่อยเป็นเมนูรอง/ส่วนท้าย (footer)
💡 ข้อค้นพบสำคัญจาก Card Sorting
ไม่ใช่ทุกการ์ดที่จะกลายเป็น “หน้า/เมนู” — การ์ดที่เป็นการกระทำ เช่น ส่งเบาะแส, ตั้งค่ารัศมีแจ้งเตือน, แก้ไขประกาศ มักกลายเป็น “ปุ่ม/ฟังก์ชันภายในหน้า” มากกว่าจะเป็นเมนูแยก การจัดกลุ่มช่วยให้เราเห็นว่าอะไรควรเป็นหน้า และอะไรควรเป็นการกระทำในหน้า ซึ่งเป็นวัตถุดิบโดยตรงของ Sitemap

2.4 Sitemap — โครงสร้างและลำดับชั้นของหน้าจอ

ผลจาก card sorting จะถูกนำมาจัดเป็น Sitemap ซึ่งเป็นแผนผังต้นไม้ (tree) ที่แสดงหน้าจอทั้งหมดและความสัมพันธ์เชิงลำดับชั้น (hierarchy) ช่วยให้ทีมเห็นภาพรวมของระบบและวางระบบนำทาง (navigation) ได้

ผลการจัดกลุ่ม 5 กลุ่มในหัวข้อ 2.3 กลายเป็นเมนูหลัก (top-level navigation) และโครงของ Sitemap ภาพด้านล่างแสดงภาพรวม 5 เมนูหลัก ส่วนรายการเต็มทุกหน้าจอแสดงเป็นแผนผังต้นไม้ถัดจากภาพ

Sitemap ฉบับเต็มของแอปค้นหาสัตว์เลี้ยงหาย

กลุ่ม/เมนูหลัก หน้า (page) การกระทำในหน้า (action)
  • หน้าแรก (Home)
    • 1. แจ้งเรื่องสัตว์
      • แจ้งสัตว์เลี้ยงหาย
        • เลือก/ถ่ายรูปสัตว์
        • ระบุพิกัด/สถานที่
      • แจ้งพบสัตว์จร
    • 2. ค้นหา/ดูประกาศ
      • ประกาศสัตว์หายทั้งหมด
        • ค้นหาตามพื้นที่
        • กรองตามประเภทสัตว์
      • แผนที่จุดพบเห็นล่าสุด
      • รายละเอียดประกาศ
        • รูปภาพสัตว์
        • ส่งเบาะแส
        • แชต/โทรหาเจ้าของ
        • แชร์ประกาศไปโซเชียล
        • รายงานประกาศไม่เหมาะสม
    • 3. การแจ้งเตือน
      • การแจ้งเตือนสัตว์หายใกล้ฉัน
      • ตั้งค่ารัศมีแจ้งเตือน
    • 4. บัญชีของฉัน
      • เข้าสู่ระบบ / สมัครสมาชิก
      • โปรไฟล์ผู้ใช้
        • แก้ไขข้อมูลส่วนตัว
      • ประกาศของฉัน
        • แก้ไขประกาศ
        • ปิดประกาศ (เจอแล้ว)
      • บันทึก/ติดตามประกาศ
      • ประวัติการแจ้ง
    • 5. ช่วยเหลือ
      • คำถามที่พบบ่อย (FAQ)
      • ติดต่อทีมงาน
กรณีศึกษา: เชื่อมโยงโอกาสจากบทที่ 5 สู่โครงสร้าง

โอกาส “ฟอร์มแจ้งหายสั้น” → กลายเป็นหน้า แจ้งสัตว์เลี้ยงหาย  |  โอกาส “รวมเบาะแสไว้ที่เดียว” → กลายเป็นหน้า รายละเอียดประกาศ (พร้อมการกระทำ ส่งเบาะแส/ติดต่อ)  |  โอกาส “แจ้งเตือนคนใกล้เคียง” → กลายเป็นกลุ่ม การแจ้งเตือน

2.5 User Flow และ Task Flow

เมื่อรู้ว่ามีหน้าจออะไรบ้างแล้ว ขั้นต่อไปคือออกแบบ User Flow — เส้นทางที่ผู้ใช้เดินผ่านหน้าจอต่าง ๆ เพื่อทำงานหนึ่งให้สำเร็จ ส่วน Task Flow เน้นลำดับขั้นของงานเดียวที่ชัดเจน เราเขียนด้วยสัญลักษณ์ผังงาน (flowchart) มาตรฐาน

ตัวอย่าง User Flow: งาน “แจ้งสัตว์เลี้ยงหาย”

ตัวอย่าง User Flow เพิ่มเติม (เขียนด้วย Mermaid)

🔑 จุดที่ต้องเข้าใจ
Sitemap ตอบว่า “มีหน้าอะไรบ้างและจัดวางอย่างไร” (โครงสร้างนิ่ง) ส่วน User Flow ตอบว่า “ผู้ใช้เดินผ่านหน้าเหล่านั้นอย่างไรเพื่อทำงานให้สำเร็จ” (เส้นทางเคลื่อนไหว) ทั้งคู่ต้องสอดคล้องกัน
⚠️ ข้อผิดพลาดที่พบบ่อย
  • จัดเมนูตามโครงสร้างองค์กร/ฐานข้อมูล แทนที่จะจัดตาม mental model ของผู้ใช้
  • ลำดับชั้นลึกเกินไป ทำให้ผู้ใช้ต้องกดหลายครั้งกว่าจะถึงเป้าหมาย
  • User flow ลืมเส้นทางผิดพลาด เช่น กรณีข้อมูลไม่ครบหรือยังไม่ล็อกอิน ทำให้ออกแบบไม่ครบสถานการณ์จริง

เชื่อมโยงสู่การพัฒนาเว็บ: จาก Sitemap สู่โครงสร้างเส้นทาง (Routes)

Sitemap แปลงเป็นโครงสร้างเส้นทาง (routing) ของเว็บแอปได้โดยตรง ลำดับชั้นของหน้าจอสอดคล้องกับลำดับของ URL ซึ่งเป็นพื้นฐานสำคัญในวิชาการพัฒนาเว็บแอปพลิเคชัน

// Sitemap → routing ของเว็บแอป (สอดคล้องลำดับชั้นหน้าจอ)
const routes = [
  { path: "/",              page: "Home" },
  { path: "/report-lost",   page: "ReportLost" },
  { path: "/report-found",  page: "ReportFound" },
  { path: "/browse",         page: "Browse" },
  { path: "/browse/:postId", page: "PostDetail" },   // หน้าลูกของ browse
  { path: "/alerts",         page: "Alerts" },
  { path: "/profile",        page: "Profile" }
];

3. สรุปท้ายบท

  • Information Architecture คือการจัดระเบียบ ตั้งชื่อ และนำทางเนื้อหา ให้สอดคล้องกับ mental model ของผู้ใช้
  • Card Sorting (เปิด/ปิด) ช่วยค้นหาว่าผู้ใช้คาดหวังให้เนื้อหาถูกจัดกลุ่มอย่างไร
  • Sitemap แสดงหน้าจอทั้งหมดและลำดับชั้น เป็นพื้นฐานของระบบนำทาง
  • User Flow / Task Flow แสดงเส้นทางการทำงานด้วยสัญลักษณ์ผังงาน ต้องครอบคลุมจุดตัดสินใจและเส้นทางผิดพลาด
  • Sitemap และ User Flow ต้องสอดคล้องกัน และต่อยอดมาจากโอกาสใน journey map โดยตรง

4. คำถามทบทวน (ไม่เก็บคะแนน)

Information Architecture คืออะไร และเหตุใดจึงต้องสอดคล้องกับ mental model ของผู้ใช้

จงร่าง user flow ของงาน “แจ้งพบสัตว์จร” ว่าควรมีจุดตัดสินใจตรงไหนบ้าง

บทนี้มี workshop 2 คาบ โดยใช้ sticky note/กระดาษหรือ FigJam/Miro ห้ามใช้เครื่องมือ AI

📅 สัปดาห์ที่ 6 — Card Sorting & Sitemap
  1. ทบทวนโอกาสจากบทที่ 5 (15 นาที)
    รวบรวมโอกาส/ฟีเจอร์ทั้งหมดจาก journey map มาเขียนลงการ์ด
  2. Card Sorting (35 นาที)
    ทำ open card sorting กับเพื่อนต่างกลุ่ม 3–5 คน เพื่อดูว่าผู้ใช้จัดกลุ่มอย่างไร

    นำผล card sorting มาจัดเป็นแผนผังต้นไม้ กำหนดลำดับชั้นและชื่อเมนู (labeling)
  4. Peer Review (20 นาที)
    สลับ sitemap กับอีกกลุ่ม ตรวจว่าผู้ใช้น่าจะหาเมนูเจอหรือไม่
📅 สัปดาห์ที่ 7 — User Flow
  1. ทบทวนสัญลักษณ์ผังงาน (15 นาที)
    ทบทวนสัญลักษณ์ผังงาน (start/end, process, decision, ทิศทาง) ร่วมกัน แล้วลองวาดสัญลักษณ์แต่ละแบบ
  2. เขียน User Flow งานหลัก (40 นาที)
    เขียน flow ของงาน “แจ้งสัตว์หาย” ครบจุดตัดสินใจและเส้นทางผิดพลาด
  3. เขียน Flow งานรอง (30 นาที)
    เลือกอีก 1 งาน (เช่น “ค้นหา/ดูประกาศ” หรือ “แจ้งพบสัตว์”) มาเขียน flow
  4. ตรวจความสอดคล้อง & เตรียม Midterm (25 นาที)
    ตรวจว่า flow สอดคล้องกับ sitemap และรวบรวมผลงานบท 1–6 เตรียมนำเสนอสอบกลางภาค
